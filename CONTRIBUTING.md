# Contributing

**Help builders create clearer, more dependable agentic systems. Every focused contribution can strengthen this shared knowledge base.**

## Contributions We Welcome

- Relevant resources with accurate, original descriptions.
- Clear explanations of harness engineering concepts.
- Reproducible examples of modular automation.
- Corrections, broken-link fixes, and accessibility improvements.
- Architecture case studies with documented outcomes and limitations.

## Contribution Workflow

1. Check existing content and open discussions to avoid duplication.
2. For substantial changes, open an issue describing the problem and proposed scope once this project is hosted.
3. Create a focused branch in your working copy.
4. Make one coherent change and update related documentation.
5. Check Markdown formatting, links, and any affected code behavior.
6. Submit a pull request explaining the change and its validation.

Until a remote repository is published, contributions can be prepared as a local patch or shared for maintainer review.

## Resource Submissions

Add entries to the relevant category in `docs/resources.md`. Include the title, direct URL, author or maintainer, intended audience, and a concise explanation of relevance. Prefer primary sources and disclose commercial affiliation when relevant.

Do not copy substantial source material or submit unsupported benchmark claims. Respect third-party licenses and clearly identify paid or restricted resources.

## Documentation Style

- Use professional, encouraging language and concise explanations.
- Organize content with descriptive headings and focused bullet points.
- Define unfamiliar terms and use concrete examples.
- Distinguish implemented behavior from proposals and future work.
- Keep project-relative links usable from the repository.

## Code Sample Expectations

Provide setup instructions, declared dependencies, expected behavior, and known limitations. Include meaningful checks for failure paths. Never commit credentials, personal data, or real customer records.

## Pull Request Checklist

- [ ] The change has a clear purpose and focused scope.
- [ ] Sources and external claims are attributed.
- [ ] Links and formatting have been checked.
- [ ] Code behavior has been validated where applicable.
- [ ] Limitations and prerequisites are documented.
- [ ] No secrets or confidential information are included.

## Community Conduct

Be respectful, constructive, and specific. Review ideas on their merits, welcome different experience levels, and help contributors improve their work.
